vonNeuro network · connecting a device

Connecting a device

A connected device stays in the laboratory that owns it. An agent on the adjacent computer links it to vonNeuro Messenger; a short driver declares the operations the device supports and their limits; the owner decides who may use it. Messenger provides accounts, queueing, metering and the return of results.

Node registration is reviewed: any account can register a node from My hardware, and each new node is approved before it pairs. To discuss a device first, write to us.

What a device must provide

Any bench instrument, chip or set-up can be connected, as long as its owner provides three things:

1 · Access to its input

The way a job drives the device: the voltages, pulses, settings or data it accepts, each with its allowed range. In the driver these are the parameters of each operation, so nothing outside the range ever reaches the hardware.

2 · Access to its output

What the device returns: the currents, traces, samples or images it measures, written by the driver as result files that the user receives at the end of each job.

3 · A description

What the device is and what it does, in words a user can act on: its physics, what each operation is for, its limits and a first example. It becomes the device's page on the hub.

Free or paid

The owner sets the terms of each device on My hardware → Terms:

  • Free. Users run the device on their own account time; nothing is charged for the device.
  • Paid. The owner sets a price per hour in US dollars. Users see the price on the device's card before they run anything. Time is counted as execution time, in started seconds per job, including the instrument's set-up and excluding time spent in the queue. A device at $60 per hour costs $0.0167 per second.

Terms can be changed at any time and apply to jobs started afterwards. Who may use the device is a separate choice: every account, only accounts the owner grants time, or only the node's admins. Card payments are not open yet. Until they are, the price is shown but not charged, and the start of charging will be announced in advance.

Outbound connection only

The agent connects out to the hub over HTTPS. Nothing listens on the laboratory network and no port is opened.

Limits set by the driver

The driver checks every job before anything is driven. The hub can narrow what reaches a device, never widen it.

Access set by the owner

New devices start private. Owners share them with every account, with selected users, or with nobody, and can switch them off or disconnect at any time.

Procedure

  1. Describe the device in a driver. A short Python class lists the devices and the operations they offer, each with typed parameters and their ranges (a voltage up to 1 V, a channel from 0 to 15). Its check() rejects unsafe requests; its run() drives the hardware and writes the result files.
  2. Register and pair the computer. Sign in to Messenger, open My hardware, register the node (registration is reviewed), and obtain a one-time pairing code, which the agent exchanges for the node's own secret. The account that registers a node owns it and can add colleagues as node admins.
  3. Run the agent. The devices appear on the network with their operations. Users run them from the website, the Python lab, VS Code or their own Python, and the owner sees who ran what, for how long and with how much energy delivered.

On the computer next to the hardware

pip install https://hub.vonneuro.com/downloads/vonneuro-node.zip   # Python 3.11+
vonneuro-node pair --hub https://hub.vonneuro.com --code ABCD-EFGH
vonneuro-node check          # validates your driver's operations, offline
vonneuro-node run            # connects; your devices go online
vonneuro-node service install   # optional: start it at logon

The default configuration uses a simulated RC circuit, so the full job path can be tested before real hardware is attached.

Writing a driver

import json
from vonneuro_node import Driver, DeviceSpec, Operation, RunResult
import my_lab.probe_station as instrument          # your existing control code

class CrossbarDriver(Driver):
    def devices(self):
        return [DeviceSpec(slug="crossbar-8x8", name="8×8 memristor crossbar", kind="memristor",
            specs={"cells": 64, "max_voltage_v": 1.0},
            operations=[Operation("read", "Read one cell at a small voltage",
                params={"row": {"type": "integer", "minimum": 0, "maximum": 7},
                        "col": {"type": "integer", "minimum": 0, "maximum": 7},
                        "voltage": {"type": "number", "exclusiveMinimum": 0, "maximum": 0.3,
                                    "unit": "V", "default": 0.1}},
                result="read.json")])]

    def check(self, slug, operation, params, ctx):
        return None if instrument.ready() else "The probe station is busy"

    def run(self, slug, operation, params, ctx):
        current = instrument.read(params["row"], params["col"], params["voltage"])
        (ctx.output_dir / "read.json").write_text(json.dumps({"current_a": current}))
        return RunResult(exit_code=0, usage_seconds=0.2)

Set [driver] class = "your_module:CrossbarDriver" in node.toml. The agent keeps a local journal of every job it ran, independent of the hub's records.

Two example drivers come with the agent: drivers/simulated.py, the shortest starting point, and drivers/bench.py, the driver of the laboratory bench used in the worked examples. That bench is an ordinary node, paired the same way: its RC board and memristor array sit behind multiplexers, and its safety rules are written in its driver. A driver can also declare settings that node admins change from the website, a device page, and VOLT support through a single drive function.

Terms

  • Ownership. The device and its data remain the owner's, in the owner's laboratory. Switching it off or disconnecting the node stops its jobs.
  • Safety. The driver's checks are the final decision on what reaches the hardware. Messenger checks parameters against the declared ranges but has no knowledge of the device itself.
  • Records kept by the hub. Accounts, job records (who ran which operation, with which parameters, for how long) and the result files the driver returns, for the retention period set on the device (indefinitely, or 1 to 365 days).
  • Directory listing. A device is listed publicly only after review. A device that misbehaves or is reported may be unlisted or switched off, and its owner is informed.
  • Availability. The network is offered as is, without guarantees of availability. Each device's terms (free, or paid at the owner's hourly price) are shown on its card; the hub's own hardware is free.
